# EC 风扇协议 — 荣耀 MagicBook Pro 16（DRA-XX）

以下内容全部从这台机器自己的 ACPI 表中逆向得出（`RDER`、`WTER`、`GFNS`、`SFCS` 四个方法），
唯有 `FSVL` 的编码无法静态推导，是实测得到的。固件源码片段见
[ASL-EVIDENCE.md](ASL-EVIDENCE.md)。

## 1. 两个 EC 窗口

```asl
OperationRegion (ERAM, SystemMemory, 0xFE0B0300, 0x0100)   ; EC RAM 镜像（256 字节）
OperationRegion (SMA2, SystemMemory, 0xFE0B0400, 0x0080)   ; 命令信箱
```

两者都声明为 `QWordAcc, Lock`。这一点很关键：ACPI 解释器会用 **64 位**读写访问它们，
并且获取 **ACPI 全局锁**。驱动必须照做，否则会与固件自己的 AML 产生竞态。
`honor_fan` 使用 64 位读-改-写并调用 `acpi_acquire_global_lock()`。

### ERAM — 传统 256 字节 EC 空间

通过与内核 thermal zone 交叉验证确认：

| 偏移 | 字段 | 含义 |
|---|---|---|
| `0x20`–`0x29` | `TP00`–`TP09` | 温度探头，°C，有符号 |
| `0x2B` | `TP0A` | 温度探头 |
| `0x1F` | `GDTS` | 是一个**温度**（有符号），不是风扇值 |
| `0x79` | `ZNCJ` | 次要风扇句柄，固件默认值 `0xA0` |
| `0x08` | `FNLK`/`FNST` | Fn 锁状态 |

实机确认的对应关系：`TP00`=CPU/`TCPU`、`TP01`=`SEN2`、`TP03`=`SEN5`、`TP04`=`SEN3`、
`TP05`=`SEN8`、`TP06`=`SEN7`、`TP08`=`SEN6`、`TP09`=`SEN4`、`TP0A`=`SEN1`。

**这个空间里没有转速表。** 这就是为什么单靠 `ec_sys` 什么也做不到。

### SMA2 — 信箱

| 偏移 | 名称 | 含义 |
|---|---|---|
| `0x00` | `CMDB` | 命令；EC 完成后将其清零 |
| `0x01` | `STAT` | 状态 |
| `0x02` | `NUMB` | 字节数（这里恒为 1） |
| `0x03` | `DAT0` | 地址位 31:24 |
| `0x04` | `DAT1` | 地址位 23:16 |
| `0x05` | `DAT2` | 地址位 15:8 |
| `0x06` | `DAT3` | 地址位 7:0 |
| `0x07` | `DAT4` | — |
| `0x08` | `DATR` | 数据输入/输出 |
| `0x09` | `DAR1` | — |
| `0x0A` | `DAR2` | — |

命令字：`0x80` 读、`0x81` 写、`0x29` 写解锁。

## 2. RDER — 读取一个扩展 EC 字节

```
RDER(addr32):
    DAT0..DAT3 = addr >> 24, >> 16, >> 8, >> 0     ; 高字节在前
    NUMB = 1
    CMDB = 0x80
    轮询直到 CMDB == 0                              ; AML 里是 256 次 Sleep(2ms)
    返回 (CMDB == 0) ? DATR : 0xFF
```

## 3. WTER — 写入一个扩展 EC 字节

注意每次写入前都有解锁握手。

```
WTER(addr32, value):
    DATR = 0x4D                     ; 字符 'M'
    CMDB = 0x29                     ; 解锁
    轮询直到 CMDB == 0
    若 CMDB != 0: 返回 0xFF

    DAT0..DAT3 = 地址各字节，高位在前
    DATR = value
    NUMB = 1
    CMDB = 0x81
    轮询直到 CMDB == 0
    返回 (CMDB == 0) ? 0 : 0xFF
```

## 4. 风扇寄存器

来自 `GFNS`（读取风扇转速）——正是从这里得知机器有**两个**风扇：

| 扩展地址 | 含义 |
|---|---|
| `0x20020A00` / `0x20020A01` | 风扇 1 转速，低/高字节 |
| `0x20020A02` / `0x20020A03` | 风扇 2 转速，低/高字节 |
| `0x20020A04` | 风扇 1 目标转速（ASL 中乘以 100） |
| `0x20020A05` | 风扇 2 目标转速 |

转速为小端 16 位：`lo | (hi << 8)`。

来自 `SFCS`（设置风扇转速）——整个固件中**唯一**的风扇写入路径：

| 扩展地址 | ASL 名称 | 含义 |
|---|---|---|
| `0x20020A1B` | `FSUD` | 手动模式开关 |
| `0x20020A1C` | `FSVL` | 手动转速值 |

```asl
Method (SFCS, 1, NotSerialized) {
    CreateByteField (Arg0, 0x02, FSUD)
    CreateWordField (Arg0, 0x03, FSVL)
    WTER (0x20020A1B, FSUD)
    WTER (0x20020A1C, FSVL)
}
```

`FSVL` 虽然声明为**字**（word），但 `WTER` 写入时 `NUMB = 1`，所以实际只有低字节到达 EC。

## 5. FSVL 编码（实测得出，非推导）

`SFCS` 从未用字面常量调用过，因此量纲只能实测。诀窍是：写入后立刻读**目标**寄存器
`0x20020A04`——它会即时更新，而转速表要滞后几十秒等风扇爬升，是不灵敏的指标。

写入 `FSUD=1, FSVL=v` 后读取 `0x0A04`：

| FSVL | 10 | 20 | 30 | 40 | 50 | 60 | 80 | 100 |
|---|---|---|---|---|---|---|---|---|
| `0x0A04` | 26 | 36 | 46 | 56 | 66 | 76 | 96 | 116 |
| 目标 rpm | 2600 | 3600 | 4600 | 5600 | 6600 | 7600 | 9600 | 11600 |

完全线性，且截距恰好等于自动模式下的怠速读数（风扇 1 为 `0x10`=16，风扇 2 为 `0x0E`=14）：

```
目标转速 = (base + FSVL) × 100        base = 16（风扇 1）、14（风扇 2）
```

所以 `FSVL` 是在怠速之上的增量，单位 100 rpm。`FSVL = 0` 给出怠速（约 1600 rpm），
绝不是关闭。风扇上限约 5800 rpm，因此 `FSVL` 超过约 42 就是在请求硬件达不到的转速。

## 6. 三个必须处理的行为

### 6.1 释放要清两个寄存器——还要分开写

只写 `FSUD = 0` 来把控制权交还固件是**不够的**。残留的旧 `FSVL` 值会让 EC 锁死在
双风扇停转状态，并且忽略后续所有写入。两个都必须清零——但**不能连着写**：
跨 manual→auto 跳变的 `(0,0)` 连写同样会锁死 EC。能用的释放是分步的，每步之间
静置几秒：

```
WTER(0x20020A1C, 0)     # 先退到怠速手动
... 静置 ...
WTER(0x20020A1B, 0)     # 再交还控制权
... 静置 ...
```

### 6.2 EC 在连续背靠背写入下会失步

每次写入都是完整的"解锁+写入"握手。若像驱动那样在几微秒内连续发出，EC 会停止应答：
`0x0A04` 回读为 0，风扇停转。同样的序列从 shell 发出（每次 `sudo tee` 天然带来数百毫秒
间隔）却能稳定工作。

恢复方法是**停止一切信箱访问（读也算）并等待数分钟**，之后 EC 通常会自行恢复正常。
40–90 秒往往不够，很容易被误判为永久锁死；深锁死时光等也未必能回来。确定性复位是
G3 断电：关机、拔电源、长按开机键 15 秒、等一分钟再开机。普通重启清不掉 EC——
它一直有待机供电。目前没有找到能跳过这段等待的寄存器写法。

### 6.3 直接覆写没问题——释放再重武装才是 bug

EC 从不拒绝第二次写入本身。手动模式内直接覆写 `FSUD`/`FSVL`（包括冗余重写 `FSUD=1`）
可反复跟随（`set 70` → `set 50` → `set 30` 得到 4440 → 3660 → 2820 rpm）。
锁死它的是驱动包在每次变更外面的"释放再快速重武装"；即使加 1 秒沉降也不行，
去掉这个环就好了。

顺带排除的假设：`ECMT`/锁竞态（改走固件自己的 `\SFCS` 方法、同一把锁、同一
`Sleep(2ms)` 时序，复现依旧——现在写入本来就经 `\SFCS`/`WTER`，`fw_path=1`）、
被绕过的 `_Qxx` 握手（`\SFCS` 在固件内零调用者，本来就是留给 OS 的接口）、
`ZNCJ` 参与（普通 EC `0x79` 全程读回 `0xA0`，EC 从未触发 `_QF8`）。
`honor_fan` 用一次 `\SFCS` 调用写手动目标，用有间隔的单字节 `WTER` 释放，
编程后不做回读确认。

## 7. 为什么用户态做不到这件事

开启 Secure Boot 后内核运行在 `lockdown=integrity` 模式，它封锁了：

| 尝试 | 结果 |
|---|---|
| `modprobe ec_sys write_support=1` | `Lockdown: unsafe module parameters is restricted` |
| `/dev/mem` | `Operation not permitted` |
| 对 EC 端口调用 `ioperm()` | `Operation not permitted` |
| 加载未签名模块 `insmod` | `Loading of unsigned module is rejected` |

而已签名的内核模块被允许执行上述全部操作。
